| Item | Value |
|---|---|
| Target | laptop cluster, `api-factory-prod`: 2 API pods (`2dc5e04`… prod runs `d7eb8fa`), CloudNativePG 2 instances (primary + replica) |
| Data | 3 databases × 11 tables × 1M rows (≈4.9 GB incl. indexes), 5 % NULLs + edge values (`factory seed-volume`) |

## Findings

1. **OOM at the first contact with real volume** (before the test): the prod primary (512Mi, sized for an empty
   database) was OOM-killed with 16 concurrent requests: ~72 backends (pgx default pool = CPU count, 2 pods × 3
   databases × 12) + parallel workers. Fixed: Postgres sized (1–2 GiB, shared_buffers / work_mem), pools capped.
2. **Two APIs time out (> 3 s) at 1M rows**: `jobs.list-latest-job-per-type` (one per group: full scan + sort of 1M
   rows, no index on `(job_type, created_at DESC, id DESC)`), `catalog.list-products-by-category` (latest version per
   key over 1M JSON events, then the category filter). The factory's perf gate (200k rows / table) passed both.
3. **JSON-versioned tables dominate the cost**: `ListLabelsByPairs`, `GetProductLabel`, `ListProductMaster`,
   `ListLabelsByLabelCodes` = 58 % of server time (avg 150–220 ms, p99 up to 482 ms) vs 5–60 ms for plain tables.
   Same root cause as 2: "latest version per key" is computed per request.
4. **Network is most of the client latency**: server p50 4.5 ms vs client p50 57 ms (Mac → laptop over Tailscale/Wi-Fi).
5. **Observability gap**: the API exports only RPC metrics, no Go runtime (heap, goroutines, GC): the soak used
   container memory / threads instead.
6. Request generation: volume data must follow the request formats (product codes were `k123`, every request a
   validation error) — `factory seed-volume` now follows them.

## Improvements (priority)

1. Index `jobs (job_type, created_at DESC, id DESC)` as the first real goose migration (rehearsed on the restored copy).
2. JSON-versioned tables: a "current version" materialization (table maintained on write or materialized view) or an
   index on (natural key, registered_at DESC); the factory decides how "latest per key" is queried.
3. Perf gate at production volume (1M rows) for the APIs the soak found slow, or nightly perf on the restored copy.
4. Go runtime metrics in the API (`collectors.NewGoCollector`).
5. Off-site backup at a quiet minute / with `--bwlimit`, or accept the hourly bump.

## Constraints / not verified

- One machine: k6 traffic crosses Wi-Fi + Tailscale; the cluster shares CPU with dev, monitoring and backups.
- Read-only API: no write path, no locks / contention from writes.
- 1 h only (no multi-day effects: autovacuum on a write workload, log growth).
- 2 APIs excluded (time out); the mix is uniform per request, not weighted by real usage.
- Laptop thermals: 53 °C under the step load; not watched during the soak.
